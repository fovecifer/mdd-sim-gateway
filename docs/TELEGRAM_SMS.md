# Telegram 双向短信（自用 fork，开发预览）

基于上游 v1.5.2；不是上游发行版提供的功能。默认关闭，现有短信、读卡器、代理及引擎不变。
第一版仅支持一个数字用户 ID 的私聊、一张明确绑定的 SIM、VoWiFi 短信，不做蜂窝回退。
无需 AI 模型、公网入站端口、域名或额外服务器。

## 配置与使用

1. 使用自己的 Telegram 账号通过官方 [BotFather](https://t.me/BotFather) 创建专用 Bot。
   不要与其他轮询程序、Webhook 或群机器人共用。Token 只填管理页面，不贴到聊天、日志或仓库。
2. 在“通知 → Telegram”设置 Bot Token、个人私聊 Chat ID 和可用的 HTTP/SOCKS5 代理。
   “授权用户数字 ID”必须是本人，并与私聊 Chat ID 相同；不接受用户名、群或频道。
   不使用“第一个发 /start 的人就是主人”机制。
3. 打开 Telegram 通道及“双向短信”，选择已识别 ICCID 的 SIM，设置提交次数上限，保存。
   重新绑定 SIM 必须勾选“保存时明确绑定当前所选 SIM”。修改权限后旧草稿全部失效。
4. 向 Bot 发送 `/start` 或 `/help`。`/status` 查看绑定及额度配置，**不代表 IMS 已注册**。
5. 回复启用后收到的短信通知，或者输入 `/sms +国际号码 正文`。检查预览中号码、正文和线路，
   在 120 秒内点击“确认发送”。点击“取消”不会发送。`/recent` 查看最近五条草稿/发送状态。

仅接受 `+` 开头的国际号码，不猜测国家区号，不向短信短码、字母发送者、紧急服务代码发送。
正文最多 160 个 UTF-16 单位，emoji 通常占两个；中文等内容可能拆成多条计费。
默认滚动 24 小时最多 20 次提交，可设 1–100；相邻提交至少间隔 10 秒。
这是**提交次数**而非运营商计费分段数；失败/结果不明的尝试也消耗本地额度。

## 安全与可靠性

- 主人身份和私聊 ID 双重检查；消息正文、转发内容和被引用的文本不能改变收件号码。
- 通知回复目标以本地数据库的 `scope + chat + message_id` 对应关系为准，不解析展示文字。
- 管理员保存设置时产生权限版本，绑定线路 ID 和 ICCID 摘要。换卡、换用户、换 Bot、
  禁用后重启授权都会让旧确认失效。发送前再次验证权限、卡身份、卡存在性和 IMS 注册。
- 短信与 Telegram 待推送记录在同一 SQLite 事务中保存；通知失败重试，不阻塞运营商收信。
  Telegram `sendMessage` 没有本方案可用的幂等键，网络结果不明时可能出现重复通知。
  **重复通知不等于重复短信提交**：发送操作另有持久的一次性确认记录。
- 付费提交前先落盘认领草稿，提交中崩溃记为 `unknown`，绝不自动重发。
  极端崩溃窗口可能丢失一次用户指令/状态通知；用户须检查 `/recent` 和网页记录后决定下一步。
- `submitted`/`sent` 仅代表网关提交；运营商回执也不证明对方已阅读。无法确认结果时不展示“对方已收到”。
- 首次或服务重启后，过期指令不执行；Telegram 未取走的更新最多保留 24 小时。
  关闭接收模式后没有积压指令补执行。旧待推送通知会取消，不转交给新主人。
- 轮询和发送使用独立后台任务；系统文件锁避免本机多个后台进程同时消费。
  遇到现有 Webhook/其他轮询冲突只报错，不自动删 Webhook、丢弃积压更新或抢占其他程序。
- 不新增公网端点，不关闭 HTTPS、登录或 CSRF。Bot 模块仍位于管理进程内，不能视为独立沙箱。
- Bot 对话不是端到端加密。本地新增通知、草稿和映射保留最多 30 天（运行时清理），
  不自动删除普通短信记录或 Telegram 云端消息。保护数据库及备份，不记录 Token/完整异常 URL。

## 部署、更新与回滚

本预览应先在测试副本完成验证，再安排真实设备维护窗口；不要直接覆盖运行中的目录。

1. 记录当前部署 commit、服务启动方式和配置路径；备份整个私有数据目录、源码及服务配置。
   备份不提交 Git，不发送给第三方。
2. 将更新策略设为“提示更新”，不让上游官方发行版覆盖 fork。现有安装器和更新器仍保留
   上游默认来源，**不会自动识别该自用分支**。本阶段不要用官方在线安装/更新命令升级 fork。
3. 从本 fork 的功能分支制作经测试的本地构建。仅更新控制后台及 WebUI；本功能不要求重建
   引擎镜像、修改读卡器驱动或网络出口。控制后台重启会短暂中断管理与通知处理。
4. 用默认关闭状态启动，先确认网页收发和线路注册未回归，再由管理员输入 Token 和授权信息。
5. 实机验证：普通来信推送、回复确认、主动发送、取消、重复按钮、错误用户、换卡拒绝、
   重启后回复映射、代理断开恢复。真实发信只使用本人可控的号码，每次明确确认。
6. 回滚先关闭双向短信，停止该版控制进程，然后恢复之前的控制代码和 WebUI。
   新增表不改变原有表字段；旧版会忽略它们。仅在必要时恢复数据库备份，避免丢失部署后的短信。
   再次启用新版本时应重新授权；不能复用旧的待确认操作。

上游更新由维护者在独立分支合并、跑完整测试和安全检查后再部署。此文不是无人值守发布授权。

## 开发验证

```sh
python -m unittest tests.test_telegram_sms
python -m unittest discover -s tests
python -m py_compile control/app/*.py engine/*.py host/*.py
sh -n install.sh engine/entrypoint.sh
sh tools/check-subscriber-identifiers.sh
cd webui && npm ci && npm run build
```

测试使用虚构号码、假 Token、临时数据库和模拟网络/发送函数，不能代替真实 Bot 与运营商联调。

[Telegram 隐私说明](https://telegram.org/privacy)。
